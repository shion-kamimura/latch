# PR作成前のローカル差分とIssueを検証する利用仕様

この文書は、AIが生成した変更を開発者がPR作成前にLatchで検証し、必要に応じて修正・再検証したうえで、検証結果を添えたDraft PRを作成する流れの利用仕様を定義します。

> **注意**: 以下は仕様であり、Latch CLIの検証機能は未実装です。ここに書くコマンド・引数・出力は実装Issueで確定する提案であり、現在のCLIは`--help`と`--version`だけを提供します。

- 要件抽出・テスト生成・隔離実行・レポートの具体的な方式（プロバイダー、テストランナー、サンドボックス方式など）は未決定です。本書は入出力の契約と期待結果を定め、実装手段を固定しません。

## 対象とする利用の流れ

```text
AIによる変更 → Latchによる検証 → 必要に応じた修正・再検証 → 結果を添えたDraft PR
```

開発者がLatchを実行するタイミングは、変更をコミットした直後（PR作成前）を基本とします。CIでは、Draft PRに対応する差分を同じ入力契約で再検証し、手元の結果を再現できるか確認します。

## 入力

### ローカルリポジトリ

- 実行は対象リポジトリのワークツリー内で行う。Latchはカレントディレクトリをリポジトリ境界として解決し、境界外へのパス参照を入力として受け付けない。
- リポジトリ外・Git管理外のディレクトリで実行した場合は、検証せず「入力不正」として終了する。
- サブモジュールや外部依存の取得は行わない。必要な依存が手元にない場合は「実行不能・判定不能」とする。

### 比較対象（base）

比較対象は「検証したい変更の差分を決めるref」です。次のいずれかを明示的に指定します。

| 指定                     | 意味                                                       |
| ------------------------ | ---------------------------------------------------------- |
| `--base <ref>`           | 指定ref（ブランチ名・タグ・コミット）からの差分            |
| `--base`省略（ローカル） | 既定の比較対象ブランチ（例: リモート追跡のmain）からの差分 |
| `--base`省略（CI）       | PRのbaseコミット（PRのマージベース）からの差分             |

- ローカルで既定の比較対象が解決できない場合は、推測で比較せず「入力不足」として、指定可能なrefを案内する。
- 比較対象refが存在しない・取得できない場合は「入力不正」とする。

### 変更差分の範囲

差分は次の3種類に分けて扱います。取り込み方針は実装Issueで確定しますが、少なくともレポートに区分を明示します。

| 区分         | 扱い（期待）                                                           |
| ------------ | ---------------------------------------------------------------------- |
| コミット済み | 比較対象との差分として検証対象に含める                                 |
| 未コミット   | 既定では検証対象に含め、レポートに「未コミットの変更を含む」と明示する |
| 未追跡       | 既定では検証対象に**含めない**。含める場合は明示的な指定を必要とする   |

- 未追跡ファイルを既定で除外する理由は、ビルド生成物やローカルの一時ファイルを意図せず入力・送信しないためです。
- 未コミット・未追跡を含めて検証した場合、その結果はCIで再現できない可能性があるため、レポートにその旨を記録する。
- バイナリ、symlink、リポジトリ外を指すパス、`.git`配下は検証対象から除外し、除外した理由をレポートに残す。
- 差分が空の場合は、要件との対応ができないため「入力不足」として終了する。

### Issue

PRの意図・受け入れ条件の抽出元としてIssueを渡します。次のいずれかの方法を使います。

| 指定                  | 入力                                                  |
| --------------------- | ----------------------------------------------------- |
| `--issue <番号>`      | GitHubのIssue番号。該当リポジトリのIssueを取得する    |
| `--issue-file <path>` | Issue本文・タイトルを記述したローカルMarkdownファイル |
| 指定なし              | Issueなし。要件はPR本文や差分からしか抽出できない     |

- `--issue`と`--issue-file`の同時指定は「入力不正」とする。
- `--issue`指定時はリポジトリのremoteから対象リポジトリを解決する。解決できない場合、Issueが存在しない・閉じている・参照権限がない場合は「実行不能・判定不能」とし、Issue本文を勝手に補完しない。
- `--issue-file`はUTF-8の通常ファイルのみ受け付ける。存在しない・読み取れない・空の場合は「入力不正」とする。
- Issueが指定されない場合でも実行は可能とする。ただし要件は差分から推定したものに限られ、レポートの「要件不明確」「未検証」が増えることを明示する。
- GitHubへの投稿やLLMへの送信前に、対象Issue・差分が外部送信され得ることを表示し、BYOKのAPIキー利用者に確認を求める。機密コードを含む場合の扱いは未決定（後述）。

### 入力の検証順序

入力は次の順に検証し、最初に失敗した段階で停止します。複数の入力が不正な場合も、まとめて検証を開始しません。

1. リポジトリ境界とGit管理の確認
2. 比較対象refの解決
3. 差分の収集と対象外パスの除外
4. Issue入力の解決（指定時のみ）
5. 外部送信の確認

## 出力

### 出力の形式

- 既定は標準出力への人間向けテキスト（日本語）。`--json`を指定した場合は機械可読なJSONを標準出力へ出す。`--report <path>`でMarkdownファイルにも書き出す。
- 終了コードは「検証結果」ではなく「実行できたか」を表す。要件の充足は終了コードだけで判断せず、レポートを確認する。
- 標準エラーには入力不正・実行不能の理由と、次に取るべき操作（`--help`や指定方法）を出す。Issue本文・差分の内容や秘密情報はエラー出力に含めない。

| 終了コード | 意味                                                          |
| ---------- | ------------------------------------------------------------- |
| 0          | 検証を完了し、レポートを出力した（失敗・未検証を含む）        |
| 1          | 入力不正（リポジトリ外、ref不正、Issue入力不正、差分空など）  |
| 2          | 実行不能・判定不能（依存不足、Issue取得不能、実行環境の失敗） |

- 検証で要件の失敗が見つかった場合も、レポートを出せていれば終了コード0とする。CIで失敗として扱うかはワークフロー側でレポートを解釈して決める。この扱いは実装Issueで再検討する。

### レポートの必須要素

1. 実行入力の要約: リポジトリ、比較対象ref、差分の区分（コミット済み・未コミット・未追跡）、Issueの入力方法。
2. 要件: IssueやPRから抽出した要件と受け入れ条件。抽出元（Issue番号・本文箇所・差分）を示す。
3. 要件→テスト→証拠の対応: 各要件に対して、使用したテスト（既存・生成）と実行証拠を対応づける。
4. 状態: 要件・条件ごとに次のいずれかを付ける。
5. 未検証事項・要件不明確な点・除外したパス・CIとの再現性に関する注意。
6. 再検証に必要なコマンドと入力（同じbase・Issue指定を再利用できる形）。

| 状態               | 意味                                               |
| ------------------ | -------------------------------------------------- |
| 検証成功           | 特定の要件・条件について、実行したテストが成功した |
| 検証失敗           | 実行したテストが失敗し、再現可能な情報がある       |
| 未検証             | 要件は存在するが、対応する十分な検証を行えていない |
| 要件不明確         | 要求が曖昧で、期待する結果を確定できない           |
| 実行不能・判定不能 | 環境・依存関係などにより検証できなかった           |

- 実行証拠（テスト名、コマンド、終了コード、要約ログ）とLLMの解釈（要件の言い換え、生成したテストの意図）をレポート上で区別する。
- テスト成功は要件全体・コード全体の正しさの証明ではない旨をレポートに常に含める。

## 出力例（TypeScriptの小さなAPI変更）

差分の例: `formatDuration`という関数に、負の値を拒否する変更を追加した。

```diff
 export function formatDuration(ms: number): string {
+  if (ms < 0) {
+    throw new RangeError('ms must be non-negative');
+  }
   return `${ms}ms`;
 }
```

Issueの受け入れ条件の例:

```markdown
- 負の値は`RangeError`を投げる
- 0以上の値は従来どおり整形する
```

テキスト出力の例:

```text
Latch verification report

Input
  Repository: /path/to/project
  Base: origin/main
  Diff: 1 file (committed)
  Issue: #123 (GitHub)

Requirements
  R1: 負の値は RangeError を投げる            source: #123 body
  R2: 0以上の値は従来どおり整形する           source: #123 body

Coverage
  R1 検証成功    test: "rejects negative values" (generated)   evidence: exit 0
  R2 検証成功    test: "formats non-negative values" (existing) evidence: exit 0
  R2 未検証      boundary 0ms は既存テストで明示されていない

Not verified
  - R2 の境界値 0ms は生成テストでも明示確認していない
  - 未コミット・未追跡の変更は含まれていない

Re-run
  latch verify --base origin/main --issue 123

Note: Passing tests do not prove entire requirements or code correctness.
```

JSON出力も同じ要素を含み、`requirements`・`checks`・`evidence`・`status`・`unverified`・`inputs`を持つ予定です。正確なスキーマは実装Issueで確定します。

## 隔離実行と変更禁止の方針

- 検証は対象コードをホストで直接実行しない。隔離環境で実行し、ホストのGit資格情報・APIキー・ホームディレクトリ・Docker socketを渡さない。具体的な隔離方式は未決定。
- Latchは対象ソースを勝手に変更しない。生成したテストは一時領域に置き、レポートにその内容と配置先を示す。差分へ自動で追加コミットしない。
- 検証中に生成物（lockfile、ビルド成果物など）が作られても、ワークツリーへ返さない。副作用が必要な場合は人間の明示的な操作にする。
- ネットワークは隔離環境から遮断するか、LLM呼び出しだけを許可する最小構成にする。テスト実行時に外部ネットワークを必要とする場合は「実行不能・判定不能」として記録する。
- タイムアウト・リソース上限を設け、超過は「実行不能・判定不能」としてレポートする。

## 修正と再検証

1. レポートの「検証失敗」「未検証」「要件不明確」を確認し、AIまたは開発者が修正する。
2. 同じbase・Issue指定でLatchを再実行する。前回のレポートを上書きする際は、対象とした差分（コミット）が変わったかをレポートに記録する。
3. 修正をコミットして再度検証し、Draft PR作成時点の差分とレポートの差分が一致することを確認する。

## CIでの利用例

Draft PRで、同じ入力契約をCI側で再現します。

```yaml
# 例示のみ。実装時はワークフローと権限を別途レビューする
- run: latch verify --base "origin/${{ github.base_ref }}" --issue "${{ github.event.pull_request.number }}" --json > latch-report.json
```

- CIでは未コミット・未追跡の変更は存在しないため、レポートはコミット済み差分に基づく。
- ローカルで未コミットを含めて検証した場合、CIの結果と一致しない可能性があるため、PR作成前にコミットして再検証することを推奨する。
- レポートをPR本文・コメントへ添付する具体的な方法は未決定。CIで失敗扱いにする条件も未決定。

## 異常時の扱い

| 状況                                       | 扱い                                   |
| ------------------------------------------ | -------------------------------------- |
| リポジトリ外・Git管理外で実行              | 入力不正（終了コード1）、検証しない    |
| 比較対象refが解決できない                  | 入力不正（終了コード1）                |
| 差分が空                                   | 入力不足（終了コード1）、検証しない    |
| Issueが存在しない・閉じている・権限がない  | 実行不能・判定不能（終了コード2）      |
| Issue入力が空・同時指定・不正パス          | 入力不正（終了コード1）                |
| 依存関係の取得失敗・テストランナー起動失敗 | 実行不能・判定不能（終了コード2）      |
| タイムアウト・リソース上限超過             | 実行不能・判定不能（終了コード2）      |
| LLM APIの失敗（認証・上限・タイムアウト）  | 実行不能・判定不能（終了コード2）      |
| 要件が差分から確定できない                 | 検証を継続し、状態「要件不明確」を記録 |

- LLMに依存する段階（要件抽出・テスト生成）が失敗しても、既存テストだけで確認できる範囲を「検証成功／失敗」として出すか、全体を「実行不能」とするかは未決定。部分結果を出す場合は、LLM段階が失敗したことを明示する。
- 出力途中で失敗した場合、書きかけのJSONやMarkdownは成功レポートとして扱わない。

## 未決定事項

- 要件抽出・テスト生成の具体的な方式と、人間による要件確認の仕組み。
- 生成テストの保存・再利用方法、既存テストとの重複排除。
- 隔離方式（コンテナ等）と安全境界、ネットワーク制御の実装。
- レポートの正確なJSONスキーマとMarkdownテンプレート。
- 検証失敗時にCLIの終了コードを変えるか、CIで失敗扱いにする条件。
- 未追跡ファイル・未コミット変更をオプトインで含める際のフラグ名。
- LLMプロバイダー、コスト制御、機密コードの送信可否。
- GitHub Issue取得の認証方法（`gh` CLI、トークン、remote推定）。
- ブラウザE2EをMVPに含めるか。

## 後続の実装Issueへの分割案

以下は依存順の案であり、各Issueの正式な設計は別途行います。

1. **入力解決**: リポジトリ境界、base ref、差分の区分（コミット済み・未コミット・未追跡）、Issue入力（`--issue`／`--issue-file`）と入力不正式の定義、終了コード。
2. **差分とIssueからの要件抽出**: 抽出結果と抽出元の対応、要件不明確の表現。
3. **既存テストの調査と不足シナリオの生成**: 生成テストの一時配置と対象ソース非変更の担保。
4. **隔離実行と証拠収集**: タイムアウト・リソース上限、ネットワーク制御、実行不能の記録。
5. **要件→テスト→証拠レポート**: テキスト・JSON・Markdown出力、状態の付与。
6. **CI連携とDraft PRへの添付**: ワークフロー整備、レポートのPR添付方法、失敗扱いの決定（対象外の自動マージは含めない）。
