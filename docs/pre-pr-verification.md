# PR作成前のローカル差分とIssueを検証する利用仕様

この文書は、AIが生成した変更を開発者がPR作成前にLatchで検証し、必要に応じて修正・再検証したうえで、検証結果を添えたDraft PRを作成する流れの利用仕様を定義します。

> **注意**: 入力解決（#23）だけを実装済みです。要件抽出・テスト生成・隔離実行・レポートは未実装です。以下は仕様であり、実装Issueで確定する提案を含みます。

- 要件抽出・テスト生成・隔離実行・レポートの具体的な方式（プロバイダー、テストランナー、サンドボックス方式など）は未決定です。本書は入出力の契約と期待結果を定め、実装手段を固定しません。

## 実装済みの入力解決（#23）

`latch verify` は後続処理へ渡す入力スナップショットだけを解決します。この段階の出力は「検証成功」「検証完了」を表しません。

```sh
latch verify --base <ref> --issue-file <path> [--include-untracked <path>]... [--json]
```

- リポジトリ境界は `git rev-parse --show-toplevel` で確定し、Issueファイルと未追跡指定は境界内の通常ファイルに限定する。symlinkは受け付けない。
- `--base` 省略時は `origin/HEAD`、`origin/main`、`main` の順で存在するrefだけを使う。どれも解決できなければ推測せず、`--base <ref>` の明示を案内して終了コード1を返す。
- 比較は指定baseとHEADのmerge-baseから行う。指定ref自体が分岐している場合でも、base側だけの移動を差分へ混ぜない。指定baseとmerge-baseはスナップショットへ記録する。
- コミット済み差分と未コミット差分（staged・unstaged）を別々に保持する。未追跡は既定で除外し、件数とパスを警告する。`--include-untracked <path>` で明示した未追跡の通常テキストファイルだけを取り込む。
- バイナリ、symlink、submodule、`.git` 配下、境界外パスは除外し、理由を保持する。除外後に検証対象の差分が空なら終了コード1とする。
- Issueファイルはリポジトリ内のUTF-8通常ファイルで、空でなく、Markdownの `# タイトル` を持つものを受け付ける。先頭のfront matterにある `state`／`status` と `source`／`url` は分かる範囲で保持し、`closed` を理由に入力を拒否しない。形式不正・不存在・空は終了コード1とする。
- 入力読取は読み取り専用のGit引数配列とファイル読取だけで行い、シェル解釈・外部送信・対象ソースの変更を行わない。
- 入力は解決時点のスナップショットとして固定する。`head`、base、merge-base、コミット済み・未コミットの差分本文、明示した未追跡ファイル内容、Issue内容からSHA-256の識別子を作り、後続処理は再計算せず同じスナップショットを使う。
- 未コミットまたは明示した未追跡ファイルを含む場合、CIでは同じ内容を再現できないことをスナップショットへ記録する。再実行に使うコマンドも出力する。
- JSONは `phase: "input-resolution"`、`verification: "not-run"` と、base・差分区分・Issue・除外理由・再現性・digestを含む。テキスト出力も同じ要素を日本語で示す。

## 対象とする利用の流れ

```text
AIによる変更 → Latchによる検証 → 必要に応じた修正・再検証 → 結果を添えたDraft PR
```

開発者がLatchを実行するタイミングは、変更をコミットした直後（PR作成前）を基本とします。CIでは、Draft PRに対応する差分を同じ入力契約で再検証し、手元の結果を再現できるか確認します。

## 入力

### ローカルリポジトリ

- 実行は対象リポジトリのワークツリー内で行う。Latchはカレントディレクトリをリポジトリ境界として解決し、境界外へのパス参照を入力として受け付けない。
- リポジトリ外・Git管理外のディレクトリで実行した場合は、検証せず「入力不正」として終了する。
- 依存・submoduleは、利用者が許可した宛先・用途・固定revisionの隔離準備工程で取得できる。許可がない、取得できない、または隔離できない場合は「実行不能・判定不能」とする。元のワークツリーを更新しない。

### 比較対象（base）

比較対象は「検証したい変更の差分を決めるref」です。次のいずれかを明示的に指定します。

| 指定                     | 意味                                                       |
| ------------------------ | ---------------------------------------------------------- |
| `--base <ref>`           | 指定ref（ブランチ名・タグ・コミット）からの差分            |
| `--base`省略（ローカル） | 既定の比較対象ブランチ（例: リモート追跡のmain）からの差分 |
| `--base`省略（CI）       | PRのbaseコミット（PRのマージベース）からの差分             |

- ローカルで既定の比較対象が解決できない場合は、推測で比較せず「入力不足」として、指定可能なrefを案内する。
- 比較対象refが存在しない・取得できない場合は「入力不正」とする。

### 変更差分の範囲

差分は次の3種類に分けて扱います。取り込み方針は実装Issueで確定しますが、少なくともレポートに区分を明示します。

| 区分         | 扱い（期待）                                                           |
| ------------ | ---------------------------------------------------------------------- |
| コミット済み | 比較対象との差分として検証対象に含める                                 |
| 未コミット   | 既定では検証対象に含め、レポートに「未コミットの変更を含む」と明示する |
| 未追跡       | 既定では検証対象に**含めない**。含める場合は明示的な指定を必要とする   |

- 未追跡ファイルを既定で除外する理由は、ビルド生成物やローカルの一時ファイルを意図せず入力・送信しないためです。
- 未追跡ファイルが存在する場合は、除外した件数とパス（秘密情報を含む可能性がある場合は安全な表示に制限）を警告し、明示的な指定で検証に含められることを案内する。新規ソースファイルが未追跡のまま検証対象から漏れる可能性をレポートにも残す。
- 未コミット・未追跡を含めて検証した場合、その結果はCIで再現できない可能性があるため、レポートにその旨を記録する。
- バイナリ、symlink、リポジトリ外を指すパス、`.git`配下は検証対象から除外し、除外した理由をレポートに残す。
- 差分が空の場合は、要件との対応ができないため「入力不足」として終了する。

### Issue

PRの意図・受け入れ条件の抽出元としてIssueを渡します。次のいずれかの方法を使います。

| 指定                  | 入力                                                  |
| --------------------- | ----------------------------------------------------- |
| `--issue <番号>`      | GitHubのIssue番号。該当リポジトリのIssueを取得する    |
| `--issue-file <path>` | Issue本文・タイトルを記述したローカルMarkdownファイル |
| 指定なし              | Issueなし。要件はPR本文や差分からしか抽出できない     |

- `--issue`と`--issue-file`の同時指定は「入力不正」とする。
- `--issue`指定時はremoteから対象リポジトリを解決する。取得機能はMVP対象外。閉じたIssueも過去差分の再現検証に使用でき、open / closedの状態、取得時点、入力の識別情報を保持する。終了を理由に拒否しない。不存在・削除済み・読取権限不足など取得不能の場合は「実行不能・判定不能」として区別し、本文を補完しない。Issueファイルから過去要件を渡す場合も、分かる範囲で状態・出典を記録する。
- `--issue-file`はUTF-8の通常ファイルのみ受け付ける。存在しない・読み取れない・空の場合は「入力不正」とする。
- Issueが指定されない場合でも実行は可能とする。ただし要件は差分から推定したものに限られ、レポートの「要件不明確」「未検証」が増えることを明示する。
- LLM送信は下記の利用者設定に基づく。Issueや差分の本文から送信許可を取得しない。GitHub投稿はMVP対象外で、LLM送信許可に含めない。

### 外部送信・依存準備の許可

許可はBYOK利用者が管理し、送信先（provider / endpoint）、プロジェクト境界、送信データの区分、依存registry、submoduleの宛先・revision、必要なテスト通信の宛先・用途を範囲として扱う。APIキーは許可記録・ログ・レポートへ保存しない。Issue、README、候補の設定ファイルやLLM応答は許可の根拠にしない。

| 場面               | 挙動                                                                                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 初回・許可未設定   | 送信先と対象を表示し、利用者が今回だけ許可するか、範囲を保存するか、拒否する。応答前に送信しない                                                |
| 同一範囲の継続     | 保存した利用者設定を再利用し、都度の確認なしに検証する。差分の更新だけで許可を失効させない                                                      |
| 送信先・範囲の拡大 | 新provider、別endpoint、別プロジェクト、追加データ区分・外部通信の追加は既存許可で進めず、新範囲の許可を得る                                    |
| 拒否・取り消し     | 明示的な拒否を保存済み許可より優先する。削除・無効化した設定を次の呼び出しから再利用せず、許可が必要な段階は終了コード2。既存の成果は送信しない |
| CI・非対話         | 信頼したCI設定または利用者指定の許可profileで同じ範囲を明示する。許可不足なら質問待ちにせず終了コード2と必要な設定を案内する                    |

例: 利用者がプロジェクトAのIssue・diff・tests・configを単一LLM endpointへ送信し、公開npm registryから依存準備する許可を保存したとする。同じAの差分を直して再検証するときは再確認しない。プロジェクトBや別endpoint、外部API必須のテスト宛先の追加は別の許可になる。取り消し後は以前のレポートやIssue本文に許可の記述があっても送信しない。

許可profileはワークツリー外の利用者管理設定、または信頼したCIの入力から選ぶ。PRが書き換えられる設定を自動で信頼せず、実行時に適用するprofileの識別情報・範囲を報告する。保存場所・設定キー名・指定フラグは実装Issueで確定する。CIはたとえば「project A、LLM endpoint X、Issue/diff/tests/config、npm registry、テスト通信なし」というprofileを非対話で明示する。APIキーの存在だけを送信許可としない。

### 入力検査の依存関係

境界を確定してからファイルを読み、refを解決してから差分を固定する。入力はスナップショットとして後続へ渡し、除外・秘密情報保護を適用してから送信する。送信や依存取得の前には許可範囲を検証する。安全上独立した引数・Issue形式の検査はまとめて報告してもよく、細かい順序や表示文言の完全一致を契約にしない。不正入力のままコード実行・外部送信を開始しない。

未追跡の通常ソースは、実装時に定める明示オプションで対象パスを指定して取り込む。たとえば新しい `src/api.ts` だけを選び、生成物や秘密情報を含めない。取り込む場合も境界・秘密情報検査を通し、元ファイルを書き戻さない。

## 出力

### 出力の形式

- 既定は標準出力への人間向けテキスト（日本語）。`--json`を指定した場合は機械可読なJSONを標準出力へ出す。`--report <path>`でMarkdownファイルにも書き出す。
- 終了コードは「検証結果」ではなく「実行できたか」を表す。要件の充足は終了コードだけで判断せず、レポートを確認する。
- 標準エラーには入力不正・実行不能の理由と、次に取るべき操作（`--help`や指定方法）を出す。Issue本文・差分の内容や秘密情報はエラー出力に含めない。

| 終了コード | 意味                                                          |
| ---------- | ------------------------------------------------------------- |
| 0          | 検証を完了し、レポートを出力した（失敗・未検証を含む）        |
| 1          | 入力不正（リポジトリ外、ref不正、Issue入力不正、差分空など）  |
| 2          | 実行不能・判定不能（依存不足、Issue取得不能、実行環境の失敗） |

- 検証で要件の失敗が見つかった場合も、レポートを出せていれば終了コード0とする。**終了コード0は要件充足を意味しない**。CIではJSONレポート内の要件別状態を判定し、検証失敗・未検証・要件不明確・実行不能をどの条件でジョブ失敗とするかを明示的に設定する。判定ポリシーや将来の`--fail-on`相当のオプションは実装Issueで確定する。

### レポートの必須要素

1. 実行入力の要約: リポジトリ、比較対象ref、差分の区分（コミット済み・未コミット・未追跡）、Issueの入力方法。
2. 要件: IssueやPRから抽出した要件と受け入れ条件。抽出元（Issue番号・本文箇所・差分）を示す。
3. 要件→テスト→証拠の対応: 各要件に対して、使用したテスト（既存・生成）と実行証拠を対応づける。
4. 状態: 要件・条件ごとに次のいずれかを付ける。
5. 未検証事項・要件不明確な点・除外したパス・CIとの再現性に関する注意。
6. 再検証に必要なコマンドと入力（同じbase・Issue指定を再利用できる形）。

| 状態               | 意味                                               |
| ------------------ | -------------------------------------------------- |
| 検証成功           | 特定の要件・条件について、実行したテストが成功した |
| 検証失敗           | 実行したテストが失敗し、再現可能な情報がある       |
| 未検証             | 要件は存在するが、対応する十分な検証を行えていない |
| 要件不明確         | 要求が曖昧で、期待する結果を確定できない           |
| 実行不能・判定不能 | 環境・依存関係などにより検証できなかった           |

- 実行証拠（テスト名、コマンド、終了コード、要約ログ）とLLMの解釈（要件の言い換え、生成したテストの意図）をレポート上で区別する。
- テスト成功は要件全体・コード全体の正しさの証明ではない旨をレポートに常に含める。

## 出力例（TypeScriptの小さなAPI変更）

差分の例: `formatDuration`という関数に、負の値を拒否する変更を追加した。

```diff
 export function formatDuration(ms: number): string {
+  if (ms < 0) {
+    throw new RangeError('ms must be non-negative');
+  }
   return `${ms}ms`;
 }
```

Issueの受け入れ条件の例:

```markdown
- 負の値は`RangeError`を投げる
- 0以上の値は従来どおり整形する
```

テキスト出力の例:

```text
Latch verification report

Input
  Repository: /path/to/project
  Base: origin/main
  Diff: 1 file (committed)
  Issue: #123 (GitHub)

Requirements
  R1: 負の値は RangeError を投げる            source: #123 body
  R2: 0以上の値は従来どおり整形する           source: #123 body

Coverage
  R1 検証成功    test: "rejects negative values" (generated)   evidence: exit 0
  R2 検証成功    test: "formats non-negative values" (existing) evidence: exit 0
  R2 未検証      boundary 0ms は既存テストで明示されていない

Not verified
  - R2 の境界値 0ms は生成テストでも明示確認していない
  - 未コミット・未追跡の変更は含まれていない

Re-run
  latch verify --base origin/main --issue 123

Note: Passing tests do not prove entire requirements or code correctness.
```

JSON出力も同じ要素を含み、`requirements`・`checks`・`evidence`・`status`・`unverified`・`inputs`を持つ予定です。正確なスキーマは実装Issueで確定します。

## 隔離実行と変更禁止の方針

- 検証は対象コードをホストで直接実行しない。隔離環境で実行し、ホストのGit資格情報・APIキー・ホームディレクトリ・Docker socketを渡さない。具体的な隔離方式は未決定。
- Latchは対象ソースを勝手に変更しない。生成したテストは一時領域に置き、レポートにその内容と配置先を示す。差分へ自動で追加コミットしない。
- 検証中に生成物（lockfile、ビルド成果物など）が作られても、ワークツリーへ返さない。副作用が必要な場合は人間の明示的な操作にする。
- 依存準備は資格情報を持たない隔離工程で、許可したregistry・submoduleだけへ接続する。manifest・lockfile・固定revisionに対応した依存を用意し、install / lifecycle scriptも未信頼コードとして隔離する。元ソース・lockfileを書き戻さない。
- テスト通信は既定で遮断する。必要な宛先・用途を利用者が明示設定できる拡張点を設け、許可範囲内だけを接続可能にする。許可・環境が不足するテストは「実行不能・判定不能」とする。生成テストや対象リポジトリからネットワーク権限を広げない。LLM接続は対象コードの実行環境から分離する。外部サービス用の資格情報注入はMVPに追加しない。
- タイムアウト・リソース上限を設け、超過は「実行不能・判定不能」としてレポートする。

## 修正と再検証

1. レポートの「検証失敗」「未検証」「要件不明確」を確認し、AIまたは開発者が修正する。
2. 同じbase・Issue指定でLatchを再実行する。前回のレポートを上書きする際は、対象とした差分（コミット）が変わったかをレポートに記録する。
3. 修正をコミットして再度検証し、Draft PR作成時点の差分とレポートの差分が一致することを確認する。

## CIでの利用例

Draft PRで、同じ入力契約をCI側で再現します。**PR番号はIssue番号ではありません**。元Issue番号を明示的に渡す例を示します（ここではIssue #15を想定）。実際のCIでは、ワークフロー入力などで関連Issue番号を受け取るか、PR本文の`Closes #15`などから関連Issueを検証付きで解決する必要があります。複数Issue・参照なし・曖昧な参照の場合の扱いは実装Issueで定義します。

```yaml
# 例示のみ。実装時はワークフローと権限を別途レビューする
# ISSUE_NUMBERは関連するGitHub Issue番号として事前に解決・検証する
- run: latch verify --base "origin/${{ github.base_ref }}" --issue "$ISSUE_NUMBER" --json > latch-report.json
  env:
    ISSUE_NUMBER: '15' # 例示用。実際にはPRに紐づくIssue番号を設定する
```

このコマンドの終了コード0だけでは検証成功と判定できません。CIの合否判定には`latch-report.json`の状態を解釈する追加ステップが必要です（判定条件は未決定）。

- CIでは未コミット・未追跡の変更は存在しないため、レポートはコミット済み差分に基づく。
- ローカルで未コミットを含めて検証した場合、CIの結果と一致しない可能性があるため、PR作成前にコミットして再検証することを推奨する。
- レポートをPR本文・コメントへ添付する具体的な方法は未決定。CIで失敗扱いにする条件も未決定。

## 異常時の扱い

| 状況                                       | 扱い                                                   |
| ------------------------------------------ | ------------------------------------------------------ |
| リポジトリ外・Git管理外で実行              | 入力不正（終了コード1）、検証しない                    |
| 比較対象refが解決できない                  | 入力不正（終了コード1）                                |
| 差分が空                                   | 入力不足（終了コード1）、検証しない                    |
| Issueが不存在・削除済み・読取不能          | 実行不能・判定不能（終了コード2）                      |
| 閉じたIssueを入力                          | 状態・出典を保持して継続し、過去要件に対する結果と明記 |
| 送信・依存・テスト通信の許可不足/取り消し  | 実行不能・判定不能（終了コード2）、無断送信しない      |
| Issue入力が空・同時指定・不正パス          | 入力不正（終了コード1）                                |
| 依存関係の取得失敗・テストランナー起動失敗 | 実行不能・判定不能（終了コード2）                      |
| タイムアウト・リソース上限超過             | 実行不能・判定不能（終了コード2）                      |
| LLM APIの失敗（認証・上限・タイムアウト）  | 実行不能・判定不能（終了コード2）                      |
| 要件が差分から確定できない                 | 検証を継続し、状態「要件不明確」を記録                 |

- LLMに依存する段階（要件抽出・テスト生成）が失敗しても、既存テストだけで確認できる範囲を「検証成功／失敗」として出すか、全体を「実行不能」とするかは未決定。部分結果を出す場合は、LLM段階が失敗したことを明示する。
- 出力途中で失敗した場合、書きかけのJSONやMarkdownは成功レポートとして扱わない。

- 生成テストの保存・再利用方法、既存テストとの重複排除。
- 隔離方式（コンテナ等）と安全境界、ネットワーク制御の実装。
- レポートの正確なJSONスキーマとMarkdownテンプレート。
- 検証失敗時にCLIの終了コードを変えるか、CIで失敗扱いにする条件。
- 未追跡ファイル・未コミット変更をオプトインで含める際のフラグ名は #23 で `--include-untracked <path>` と確定した。未コミットは既定で含める。
- 単一LLMプロバイダーの選定、コスト制御、許可profileの保存形式・指定方法。機密コードを送信するかは利用者の設定に従う。
- GitHub Issue取得の認証方法（`gh` CLI、トークン、remote推定）。
- ブラウザE2EをMVPに含めるか。
