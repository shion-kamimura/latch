# Issue設計ガイド

Latchの開発Issueを、AIと人間が共同で設計するためのガイドです。新しいチャットでは過去の会話や記憶を前提にせず、最新のリポジトリを確認してください。実装時のルールは [AGENTS.md](../AGENTS.md)、Issueの項目名と必須項目は [機能開発テンプレート](../.github/ISSUE_TEMPLATE/feature.yml) を正とします。

## チャット開始時の利用例

次の文にリポジトリURLと相談したい内容を添えて使えます。

```text
https://github.com/shion-kamimura/latch の最新の docs/issue-design.md を読み、
ガイドに沿ってIssue設計を手伝ってください。相談内容は「○○」です。
不明点は質問し、まずIssue案を提示してください。GitHubへの登録は私の承認後に行ってください。
参照できない資料があれば、その旨と必要な情報を教えてください。
```

## 1. 最新の資料を確認する

設計を始める前に、対象リポジトリと参照するブランチを確認します。通常は最新のデフォルトブランチを使い、確認したブランチ・コミットまたは確認時点を記録します。

1. [AGENTS.md](../AGENTS.md) で開発ルールと制約を読む。
2. [README.md](../README.md) で目的、実装済みの機能、開発・検証方法を読む。構想と現在利用できる機能を区別する。
3. [機能開発テンプレート](../.github/ISSUE_TEMPLATE/feature.yml) で最新の項目名、説明、必須項目を確認する。このガイドの例と差がある場合も最新のテンプレートに合わせる。
4. 相談内容に関連するコード・テスト・ドキュメントを読み、現状の動作と制約を確認する。
5. 関連する既存Issue（open・closed）やPRを確認し、重複、依存関係、決定済みの方針を把握する。関連があれば番号と関係をIssue案に記載する。

リポジトリや一部の資料を参照できない場合は、参照できなかった資料と、そのため確認できない事項を明示します。必要なファイルの内容、関連Issueの本文などの共有をユーザーに依頼してください。検索できなかった場合に「関連Issueなし」と断定したり、未確認のコードを確認済みと装ったりしてはいけません。共有された資料の範囲と時点も明示し、仮案を出す場合は不足情報と未確定事項を添えます。

## 2. 要件を壁打ちして整理する

目的／解決したい課題 → 期待する動作 → 対象・対象外 → 検証可能な受け入れ条件の順に整理します。不明点や矛盾はユーザーに質問し、回答を反映してください。未確定事項を推測で埋めず、確認済みの事実、提案、未確定事項を区別します。

### 解決したい課題

誰が、どの場面で、何に困っているか、その背景と解決する目的を記載します。機能名や実装手段だけで済ませず、現状の問題を共有します。

### 期待する動作

利用者の操作や入力に対して、どの出力・結果を期待するかを具体化します。正常系に加え、関連する異常系や境界条件も確認します。たとえばCLIの変更なら、引数、標準出力・標準エラー、終了コードを必要に応じて整理します。値や仕様が決まっていなければ質問し、既定の動作として断定しません。

### 実装スコープ

「対象」と「対象外」を明記します。1 Issueは、一つの目的について実装・レビュー・検証できる単位にします。独立して受け入れられる複数の目的や大きな前提作業が混ざる場合は、Issueの分割と依存関係を提案します。

無関係なリファクタリングや将来の機能を便乗させません。必要性が確認されていないライブラリ、内部構造、アルゴリズムなどを固定せず、期待する結果と制約を中心に記載します。実装手段の指定が必要な場合は理由を添え、大規模なアーキテクチャ変更などはAGENTS.mdの事前承認ルールに従います。

### 受け入れ条件（Acceptance Criteria）

期待する動作とスコープに対応する条件を、チェックリストで記載します。各条件は、テスト、コマンド実行、文書の確認などで合否を判定できる内容にします。「適切に動く」「使いやすい」だけで済ませず、確認する操作・対象と期待結果を具体化してください。

文書追加なら、たとえば「README.mdからガイドへのリンクを開ける」「ガイドに承認前のIssue登録を禁止するルールが記載されている」のように確認できる形にします。必要な検証方法や未検証事項の報告も整理し、実行していない検証を成功済みとして書きません。

## 3. テンプレートに沿ってIssue案を提示する

タイトルはテンプレートの接頭辞（現在は `[Feature] `）に続けて、解決する課題や実現する動作を簡潔に表します。本文は最新テンプレートの項目名・順序に合わせ、現在は次の4項目を使います。

```markdown
## 解決したい課題

## 期待する動作

## 実装スコープ

対象:

-

対象外:

-

## 受け入れ条件（Acceptance Criteria）

- [ ]
```

空欄を埋めた案とともに、参照した資料・関連Issue、参照できなかった資料、未確認・未確定事項を提示します。これらはレビュー用の補足として区別し、テンプレートの必須項目を置き換えません。未確定事項が残る場合はその影響を説明し、確定に必要な回答を求めます。

## 4. 承認を得てからGitHubに登録する

Issue案の確定とGitHubへのIssue登録は別の段階です。ユーザーが最終的なタイトル・本文と登録先リポジトリを確認できる形で提示し、その内容をGitHubに登録してよいか明示的な承認を得ます。「設計を手伝って」という依頼や案への感想だけを登録の承認として扱いません。

承認前にはIssueを作成しないでください。承認後に内容や登録先を変更する必要が生じた場合は、変更後の案について再度承認を得ます。登録する手段がない場合はその旨を伝え、ユーザーが手動登録できる確定案を渡します。登録できた場合のみ、作成されたIssueのURL・番号を報告します。
