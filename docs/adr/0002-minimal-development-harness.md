# ADR 0002: 最小構成の開発ハーネスを採用する

状態: 採用。判断日: 2026-10-25。ADR整理日: 2026-10-30。効果を測定済みという意味ではありません。

## 背景

ハーネスはAIの「作業場と手順一式」です。初参加のエンジニアや新しいセッションが、会話の記憶に頼らず、依頼を理解し、変更・検証・通常PR・報告まで進められる状態を目指します。開発用ハーネスを先に整えます。製品の未信頼コード実行・品質評価は別の責務です。

完了は、依頼と差分が対応し、必要なテスト・対象commitのCI・PRを確認でき、未検証事項を説明できることです。調査依頼では回答が成果であり、変更やPRを増やしません。失敗や中断でも、原因・安全な成果・次の操作を残します。

## 決定と一次資料

既存文書より一次資料の原則と実測を優先します。製品の目的や実行プラットフォームの制約を暗黙に変えるものではありません。各社の規模やモデルに固有の構成を必須規格としてコピーせず、最小構成で確認します。

| 一次資料                                                                                                                      | 採用する原則                                                       | 今回の判断                                                                              |
| ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| [OpenAI: Harness engineering](https://openai.com/index/harness-engineering/)                                                  | 短い入口、リポジトリ内の知識・計画、結果の可視性、機械的な境界検査 | AGENTSを地図にし、索引・アーキテクチャを整備。大規模な階層・独自lint群はまだ導入しない  |
| [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 必要な情報を選んで取得し、曖昧・過剰な指示を避ける                 | 作業別の参照先とルールの正本を決め、全資料の常時読込を要求しない                        |
| [Anthropic: Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)           | 増分作業、実利用経路の確認、進捗・Git履歴で再開                    | 小さな変更をPRまで追跡し、引き継ぎ項目を用意。専用のinitializerや常駐実行器は追加しない |
| [Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)                       | 最終状態・実行記録で評価、採点器の誤りも確認、複数試行             | 代表ケースと証拠を定義。初回の少数試行をモデル性能比較や安定性の証明にしない            |
| [OpenAI: Running Codex safely](https://openai.com/index/running-codex-safely/)                                                | 技術的境界と承認方針、認証・権限の管理                             | 強制箇所と指示上の期待を一覧化。サービス側権限設定をこの変更で適用しない                |
| [Anthropic: Beyond permission prompts](https://www.anthropic.com/engineering/claude-code-sandboxing)                          | ファイル・通信の境界内で自律的に作業する                           | 確認回数削減と隔離保証を分ける。現行runnerにない境界を存在するように説明しない          |
| [Anthropic: Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)                           | 効果を測って構成を一つずつ簡素化する                               | 評価から必要な改善を選ぶ。独立レビュー役・複数エージェントは先に必須化しない            |

## 検討した代替案と変更理由

| 変更                                             | 理由                                                                                        |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| AGENTSの構想と詳細手順を製品方針・開発手順へ移す | 必須情報を見失わず、作業に応じて読み進めるため                                              |
| READMEの詳細な開発ルールを入口へ置き換える       | 複数文書の更新漏れを減らすため                                                              |
| Issue/PRの作業状況をdocsへ複製しない             | 現在地の二重管理を避けるため。文書管理は [ADR 0001](0001-documentation-ownership.md) に従う |
| 固定した数文書のリンク検査をMarkdown全体へ広げる | 新規・移動文書も検査対象にするため                                                          |
| 読取専用の環境チェックを追加する                 | Nodeの版違い・pnpm不足を、長いテストの前に原因付きで示すため                                |
| 公式連携を初回の比較基準として残す               | 独自基盤の追加効果は未測定。維持自体を絶対条件にはしない                                    |

## 影響と保証の境界

| 守ること                             | 強制・確認                                       | 証拠と停止                                           |
| ------------------------------------ | ------------------------------------------------ | ---------------------------------------------------- |
| 許可された依頼だけ実装               | workflowのauthorize                              | 認可テストとActions。照合失敗は実装開始不可          |
| 指定Node・pnpmと依存                 | manifest、lockfile、環境チェック、frozen install | 不足は終了1と対処。修復前のテストを成功扱いしない    |
| 文書の参照先が存在                   | 通常テストのファイルリンク検査                   | 参照元・対象付きで失敗。外部URL・アンカーはレビュー  |
| コードの期待動作                     | 影響層のテストと対象SHAのCI                      | 失敗・未実行を区別。テスト変更自体の妥当性もレビュー |
| 人の変更を保持、無断マージ等をしない | 指示・差分レビュー。実権限の剥奪ではない         | 競合・権限不足は状態を残す。運用上の保証限界を明示   |
| 秘密や権限の境界                     | プラットフォームの制約・サービス設定             | 認証値を記録しない。拒否を迂回しない                 |

## 継続評価

[評価ケース](../harness/evaluation.md) を実行し、[初回記録](../harness/runs/2026-10-25.md) のように条件・証拠・失敗を残します。次の作業と引き継ぎはIssue/PRへ記載します。失敗原因に対応する変更を一つずつ比較し、効果の薄い指示・検査・自動化は取り除きます。
