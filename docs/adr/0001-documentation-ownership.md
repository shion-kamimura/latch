# ADR 0001: 設計判断と作業記録の置き場所を分ける

状態: 採用。日付: 2026-10-30。

## 背景

Issue別の進行計画、PR別の受け入れ条件表、移行履歴がdocsに重複し、作業完了後も古い進捗が現行情報として残っていた。長く使う判断と一時的な作業状況を分ける必要がある。

## 決定

設計判断は主題別ADRに残す。仕様・使い方・運用は既存の正本を更新する。Issueの計画・進捗・引き継ぎ、PRの受け入れ条件への対応・レビュー状況はIssue/PR本文・コメントで管理し、それらのためのファイルを作らない。過去の該当ファイルと移動案内も削除し、履歴はGitで参照する。

PRを作成する前に、変更に関係するREADME・仕様・運用手順・ADR・索引を更新し、コードと同じPRに含める。更新不要ならPR本文に理由を記載する。PR修正で動作や判断が変わった場合も、追加commitで文書を追従させる。

日付・revision・条件を固定した評価データと実験記録は、再現・比較の証拠として保持する。今後の作業指示やPRの進捗管理には使わない。

## 検討した代替案

- Issue/PR別文書と旧URL案内を残す: 参照は維持できるが、重複と古い進捗の混入が続くため採らない。
- 判断をすべてIssue/PRだけに残す: 選定理由を横断して探しにくくなるため、長期的な判断はADRにする。

## 影響

旧文書の外部リンクは切れる。リポジトリ内の参照は更新する。設計判断・現行仕様・評価証拠の役割が分かれ、Issue/PRとの二重管理を減らせる。文書更新の確認は作業手順とレビューで行い、新しい自動判定は追加しない。
