# 開発手順

状態: 現行。環境準備・実装・検証・PR規則の正本。OpenCodeの起動・権限・費用は [運用手順](opencode.md)、Issue登録は [Issue設計](issue-design.md) を参照してください。

## 1. 対象を確かめる

対象Issueの目的・受け入れ条件と最新default branchを確認し、`git status --short` で他人の変更を調べます。新規作業は専用ブランチ、PR修正はそのheadを使います。未コミットの変更を捨てたりforce pushしたりしません。競合・権限不足では状態を残して報告します。

## 2. 環境を準備する

ビルド・テストではNode.jsを [.node-version](../.node-version)、pnpmを [package.json](../package.json) のpackageManagerに合わせます。文書だけの読取調査にはinstallや製品のビルドは不要です。

```sh
node --version
pnpm --version
pnpm install --frozen-lockfile
node scripts/check-environment.ts
```

環境チェックはネットワークアクセスやinstallをせず、Node・pnpmのバージョン、lockfile、開発依存の解決を確認します。終了コード0は準備項目の成功、1は不足です。これはテスト成功や依存の完全な整合性、隔離の安全性を証明しません。pnpmの版確認時はCorepackのnetwork取得とpnpmの自動版切替を無効化します。PATH上の実行ファイル自体は信頼できる開発ツールを使ってください。Node 24でも読取診断を試せますが、ビルド・テストには26が必要です。

pnpmがない場合は指定版を準備し、Nodeが異なる場合は既存のバージョン管理ツール等で切り替えます。接続・権限・proxyで失敗したら原因と未実行項目を記録し、承認・認証を迂回しません。依存不足を製品不具合として扱いません。

依存準備が失敗した場合は後続のlint・テストへ進まず、準備を完了してから再開します。`.node-version` の欠落・形式不正や、lockfileが通常ファイルでない場合も環境チェックは不足として案内します。

新しいheadに切り替えた場合はそのmanifestとlockfileで準備し直します。依存を意図して変更する場合だけ通常のinstallでlockfileも更新します。cache hitやbaseのinstall成功はheadの準備・テスト成功を意味しません。

## 3. 小さく変更して検証する

変更する機能の仕様・コード・既存テストを読み、実装判断の理由・仮定を残します。資料一式の読込や、同じ成功チェックの繰り返しを定型工程にしません。動作変更には必要なUnit・Integration・CLI E2Eの層でテストを追加・更新します。文書だけの変更に文言一致テストを増やす必要はありません。

実行基盤・依存・workflowなど複数層へ影響する変更では次を実行します。指示文や文書だけの変更はローカルリンク・整形と関連テストを選び、影響しない製品の全テスト・ビルドは必須にしません。

```sh
pnpm lint
pnpm typecheck
pnpm format:check
pnpm test
```

`pnpm test` はUnit・Integration → build → CLI E2Eの順です。この中のbuildが成功していれば同じ成果物を再buildする必要はありません。小さな変更では影響範囲に合う検証を選びます。CLIはbuild後に `node dist/cli.mjs --help` で確認できます。

失敗したら、今回の不具合、既存不具合、環境不足、採点・テスト側の誤りを分けます。コマンド、終了結果、対象commit、未検証事項を報告し、秘密情報をログへ残しません。

## 4. PR作成前にドキュメントを更新する

PRを作成する前に、変更に関係するREADME・仕様・運用手順・ADR・索引を確認し、実装と一致するよう更新します。文書の変更はコードと同じPRに含めます。設計上の重要な選択・変更は [ADR](adr/README.md) に背景・決定・代替案・影響を記録します。更新が不要ならPR本文の「実装内容」にその理由を書きます。PR作成後の修正でも、動作や設計判断が変わったら関連文書を追加commitで更新します。

進行計画、受け入れ条件への対応、レビュー状況、引き継ぎはIssue/PR本文・コメントに記録します。Issue番号・PR番号を主題とする文書や、同じ作業状況を複製するファイルは作りません。仕様は機能別、判断はADR、再現・比較の証拠は評価記録に分けます。方針の理由は [ADR 0001](adr/0001-documentation-ownership.md) を参照してください。

文書更新時は実装済み・未実施の記述と実行証拠を照合します。日付だけを新しくせず、限定的な成功を一般的な品質保証へ広げません。実測・進捗は正本へリンクし、複数文書へ同じ状態を複製しません。

文書更新後にローカルリンク・整形と必要なチェックを確認し、差分・受け入れ条件・文書の説明を照合してから次へ進みます。

## 5. 差分を確認して通常PRを作る

依頼された実装は、差分と受け入れ条件を照合し、専用ブランチへcommit・pushして通常PRを作成します。追加の作成承認は不要です。「案だけ」等の指定を優先し、レビュー承認・マージ・デプロイ・実権限・Secrets変更は別の操作として扱います。

PR・commitのタイトルは `<type>: <具体的な変更内容>`。主目的からtypeを選びます。

| type     | 用途                   |
| -------- | ---------------------- |
| feat     | 機能追加               |
| fix      | 不具合修正             |
| docs     | 文書のみ               |
| refactor | 動作を変えない構造整理 |
| test     | テスト                 |
| ci       | CI                     |
| chore    | 開発環境・保守         |

例: `fix: 未対応引数で終了コード1を返す`。付随するテストや文書だけで主目的のtypeを変えません。Conventional Commitsの形式をPRにも使うリポジトリ方針で、業界共通の必須規格という意味ではありません。

[PRテンプレート](../.github/pull_request_template.md) の6見出しで、動作・理由・受け入れ条件への対応、実行したテスト・結果・未検証事項を書きます。全条件を満たしたIssueだけ `Closes #番号`、親Issueの一部なら `Refs #番号` を使います。タイトルへの番号は必須ではありません。

## 6. 対象commitのCIを確認して報告する

自己テストと通常PR CIは別の実行です。PR作成時点の未実行CIは「実行待ち／未確認」とし、その後は対象SHAのChecks・Actionsログで確認します。CI終了ごとの本文同期はしません。修正したら同じPRへ追加commitして再確認します。

完了の説明には依頼に対応する差分・検証・PR・残項目を含めます。中断時は下記の引き継ぎ手順を使います。

## 中断と再開

中断時は対象Issue/PRの本文・コメントに、目的、branch・開始/現在commit、未コミット変更と保持すべき人の変更、完了・残作業、判断とADR、検証結果・未実施、PR・対象SHAのCI、停止理由・次の操作を残します。書き込みできない場合は同じ情報を最終回答に残します。専用の計画・引き継ぎファイルは作りません。

引き継ぎにはIssue/PR URLと引き継ぎコメントへのリンクを含めます。再開時はその本文・コメントを取得し、branch・SHA、status・差分を照合して、実装に必要な環境を確認します。GitHubへ接続できない、コメントが取得できない、記録とheadが違う場合は不足を示し、依存する操作を推測で進めません。取得可能なコードの調査など独立した作業は続けられます。以前の成功結果を現在の変更へ流用せず、必要な検証を選びます。
