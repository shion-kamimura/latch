# 生成テストの隔離実行と証拠収集（#25）

この文書は、`latch run` が `latch plan --json` の計画からVitestテストを生成し、固定した入力の隔離コピーで既存テストと生成テストを実行し、証拠を収集する仕様です。対象コードをホストのワークツリーで直接実行するフォールバックはありません。

`latch run` の実行結果は「検証を完了できた範囲」と「実行不能・判定不能」を分けて示します。テスト成功は要件全体・コード全体の正しさの証明ではありません。

## 利用方法

```sh
# 1. 入力と計画を固定する
latch plan --base origin/main --issue-file issue.md \
  --profile ~/.config/latch/llm-profile.json --json > latch-plan.json

# 2. 同じ入力スナップショットで生成・隔離実行する
latch run --plan latch-plan.json \
  --profile ~/.config/latch/llm-profile.json --json
```

- `latch run` は計画ファイルの `input.options` と同じ `--base`・`--issue-file`・`--include-untracked` で入力を再解決し、`input.snapshotDigest` と一致しなければ実行しません。計画後にワークツリーを変更した場合は `latch plan` をやり直します。
- `--profile` を省略した場合は `LATCH_PROFILE` を使います。許可profileはワークツリー外の利用者管理設定です。
- 終了コード0は「レポートを出力できた」ことを表し、要件充足を意味しません。計画・入力の不正は終了コード1、許可不足・隔離不能・依存準備失敗・起動失敗・時間上限などは終了コード2です。実行後に一部の条件だけ判定できない場合は部分結果を出力して終了コード2とします。

## 隔離方式と安全境界

MVPでは**固定入力の一時コピー + Node.jsのパーミッションモデル**を隔離方式とします。コンテナや仮想マシンによるOSレベル分離はこの段階では実装していません。

1. 入力は `git archive HEAD` で一時領域へ展開し、スナップショットに含まれる未コミット差分を適用し、明示指定された未追跡ファイルだけを書き込みます。
2. `evaluation/`・`cases.json`・`expected.json`・`changes/*.patch` など#22の評価専用データは隔離コピーから除外します。
3. 生成テストは隔離コピー内の `.latch/generated/` にだけ置きます。元のワークツリー・未コミット・未追跡ファイルへ書き戻しません。
4. 子プロセスは `node --permission` で起動し、読み取りを一時領域・LatchのVitest依存・Node.js本体に限定し、書き込みを一時領域に限定します。Vitestはスレッドpoolで実行します。
5. テスト通信は既定で遮断します（`--allow-net` を渡しません）。加えて、テスト実行前のsetupで`fetch`・`net`・`tls`・`http`・`https`・`dgram`の通信APIと`child_process`・`Worker`を無効化します。対象リポジトリや生成テストから`allowedDestinations`を追加しても有効になりません。
6. 子プロセスへ渡す環境変数は `PATH`・`LANG`・`LC_ALL`・`TZ`・`HOME`・`TMPDIR`・`NO_COLOR`・`CI`・`NODE_ENV` だけです。Git資格情報・APIキー・SSH agent・Docker socket・ホストのホーム設定は渡しません。
7. LLM呼び出しは対象ワークツリー外の空のcwdから公式CLIへ委譲し、対象コードの実行環境とは分離します。公式CLIだけが利用者のログインを解決し、対象テストへAPIキー・OAuthトークン変数・公式CLIのHOMEを渡しません。既知の認証パスは隔離コピーから除去します。接続の対応条件は [公式CLI接続](official-cli.md) を参照してください。
8. 時間・メモリ・出力量のLatch独自上限は既定では設けません。時間を指定した場合は超過時に子プロセスを終了し、メモリを指定した場合だけ`--max-old-space-size`を付けます。Vitestのtest/hook timeoutも未指定なら0（無効）にします。後片付けに失敗した場合はレポートへ記録します。

隔離のための一時領域を作れない、Node.jsのパーミッションモデルが使えない、依存準備やテストランナー起動に失敗する場合は、ホスト実行へ切り替えず「実行不能・判定不能」として停止します。

### 制約

- プロセス境界はコンテナではありません。同じカーネル上で動くため、OSレベルの完全な分離を保証しません。
- `--allow-addons` と `--allow-worker` はVitestの実行に必要です。生成テストから`child_process`と`Worker`の起動はsetupで拒否し、通信APIも拒否します。ただし、Node.jsの組み込み機能を直接使うような悪意あるコードの完全な封じ込めは未検証です。
- 生成テストの内容はLLMの解釈を含みます。テスト名・条件ID・実行ログを取得しても、要件の網羅性やテストの正しさを保証しません。

## 依存準備

`--profile` の `execution.dependencies.mode` で選びます。

| mode       | 挙動                                                                                                |
| ---------- | --------------------------------------------------------------------------------------------------- |
| `runner`   | 対象の依存はインストールせず、Latchに同梱されたVitestだけを隔離コピーへリンクする（既定）           |
| `offline`  | 固定lockfileに対応する依存を `pnpm install --frozen-lockfile --ignore-scripts --offline` で準備する |
| `registry` | 利用者が許可したHTTPS registryから、`--frozen-lockfile --ignore-scripts` で依存を準備する           |

- install / lifecycle scriptは未信頼コードとして扱い、既定で `--ignore-scripts` を指定します。
- registry方式では `execution.dependencies.registry` を必須にし、資格情報・query・fragmentを含むURLを拒否します。
- 隔離コピー内の `.npmrc`・`.yarnrc` は削除し、ホストや対象リポジトリの認証設定を依存準備へ渡しません。
- 元のmanifest・lockfile・ワークツリーは変更しません。依存準備に失敗した場合は実行不能として停止します。
- `runner` 方式は対象の本番依存を用意しません。対象コードが外部パッケージをimportする場合は環境不足として記録されます。
- submoduleは自動で初期化・取得しません。必要なsubmoduleが隔離コピーにない場合は環境不足として停止し、任意の宛先へ取得しに行きません。

### 実行設定の例

```json
{
  "execution": {
    "dependencies": { "mode": "runner", "registry": null },
    "network": { "allowedDestinations": [] },
    "limits": {
      "timeoutMs": null,
      "maxMemoryMb": null,
      "maxOutputBytes": null,
      "maxGeneratedFiles": null,
      "maxGeneratedFileBytes": null,
      "maxRepairAttempts": 1
    }
  }
}
```

## テスト通信の拡張点

許可profileの `execution.network.allowedDestinations` は将来の宛先単位許可の拡張点です。現在は値を定義できますが、宛先単位の通信制御は実装しておらず、値が空でない場合は実行不能として停止します。任意のネットワーク許可や外部サービス資格情報の注入をMVPへ追加していません。

## 生成テスト

- 対象は「要件不明確」ではなく、不足シナリオを持つ条件です。
- LLMへ送る内容は、条件・不足シナリオ、#22の評価専用データを除外した差分、既存Vitestテスト候補の名前・パスです。正解データや評価専用テストは送りません。
- 生成テストはVitestの `test` / `it` と `vitest` からのimportを含む必要があります。条件数・生成ファイルサイズの数値上限は、利用者が指定した場合だけ適用します。
- 構文不正やテストとして解釈できない生成物は、条件ごとの上限回数（既定1回、任意の0以上の安全な整数）だけLLMへ修正を依頼します。上限後も不正な場合は「生成テスト不正」として記録し、製品不具合の証拠にしません。
- 生成テストの修正回数・出力サイズ・タイムアウト・メモリ・生成量は許可profileのexecution.limitsで設定します。修復以外は省略またはnullが上限なし、指定時は正の安全な整数です。値を旧上限へ丸めません。推論起動の合計上限はprofileのlimits.maxRequestsです。
- 一時コピーの256 MiB制限と計画JSONの5 MiB制限も撤去しました。Node.js/OS/ディスク等の制約は残ります。上限なしの処理が終了しない場合は利用者が停止します。明示した時間上限にはNode.jsの同期プロセスAPIで表現できる範囲が適用されます。

## 状態と証拠

`latch run` は次の証拠を区別します。

| 状態             | 意味                                                 |
| ---------------- | ---------------------------------------------------- |
| 成功             | テストが実行され、アサーションが成功した             |
| アサーション失敗 | テストが実行され、期待値と実際の結果が一致しなかった |
| 生成テスト不正   | 構文不正・テストとして解釈不能・テスト0件など        |
| 起動失敗         | Vitestやテストランナーの起動に失敗した               |
| 環境不足         | 依存・import・実行環境が不足した                     |
| 時間上限超過     | 子プロセスを終了した                                 |

条件の状態は次のとおりです。

| 状態               | 意味                                                 |
| ------------------ | ---------------------------------------------------- |
| 検証成功           | 生成テストが実行され、成功した                       |
| 検証失敗           | 実行されたテストが失敗した                           |
| 未検証             | 生成テスト不正・既存テストのみ・証拠不足など         |
| 要件不明確         | 期待値を確定できないため、実行結果を検証成功にしない |
| 実行不能・判定不能 | 起動失敗・環境不足・時間上限超過など                 |

各証拠には、既存/生成の区分、条件ID、テスト名、ファイル、実行コマンド、終了コード、シグナル、実行時間、切り詰め済みログ、生成テストの内容を含めます。

## レポート（#26）

`latch run` の標準出力は、既定では日本語テキスト、`--json`では `schemaVersion: "1"` を持つJSONです。進捗・警告は標準エラーへ出し、JSON標準出力へ混ぜません。

- `input` はリポジトリ、HEAD、base、merge-base、スナップショット/差分digest、差分区分、変更ファイル、除外理由、Issue入力方法・状態・出典、再現性、計画digestを保持します。
- `requirements` は要件ごとに条件状態を集約します。集約規則は `worst-condition-state` で、優先度は「実行不能・判定不能 > 検証失敗 > 要件不明確 > 未検証 > 検証成功」です。要件内に「検証成功」以外の条件が1つでもあれば要件を検証成功にしません。状態別件数と条件別状態、非成功条件の内訳を残すため、一部成功で未検証・失敗を隠しません。
- `conditions` はLLMが解釈した条件文と出典、状態、実行証拠IDを持ちます。`evidence` は既存/生成の区分、実行コマンド、終了コード、シグナル、実行時間、切り詰め済みログを持ちます。LLMの解釈と実行証拠は別要素です。
- `verification` は `completed` または `partial` です。`partial` の場合は `partialReasons` に理由を残し、完了として表示しません。`disclaimer` にはテスト成功が要件全体・コード全体の正しさを保証しない旨を常に含めます。
- 出力前にスキーマを検証し、不正なレポートは書きかけのまま出力しません。資格情報はレポートへ含めません。

## #22の正しい変更と不具合のある変更での確認

自動テストでは `fixtures/order-api` の `changes/correct.patch` と `changes/buggy.patch` を使い、同じ生成テストが次のように分かれることを確認します。

- 正しい変更: 生成テストが成功し、条件は「検証成功」。
- 不具合のある変更: 生成テストがアサーション失敗し、条件は「検証失敗」。
- 構文不正な生成テスト: 「生成テスト不正」となり、条件は「未検証」。製品不具合の証拠にしない。
- 起動失敗: 「起動失敗」となり、条件は「実行不能・判定不能」。
- 時間上限超過: 子プロセスを終了し、「時間上限超過」として記録。
- 環境不足: 依存やimportの不足として区別し、製品不具合の証拠にしない。

固定したLLM応答を使う自動テストと、実ログインでのテスト生成品質の評価は区別します。このリポジトリの自動テストは実際の有料モデルを呼びません。
