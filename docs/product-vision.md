# 製品の目的とMVP方針

状態: 現行の製品方針。構想・未決定事項を含む。実装状況の正本は [README](../README.md)。

2026年10月21日更新の「Latch — プロジェクト構想・命名決定記録」と [Issue #4](https://github.com/shion-kamimura/latch/issues/4) を基準とする。以下は構想・初期方針であり、機能の実装完了を示すものではない。実装済みの機能は最新の [README.md](../README.md) とコード・テストで確認する。

## 目的と中心フロー

Latchは、AIが生成したコードがPRの要求を満たすかを、実際のテスト実行と証拠に基づいて検証するOSSの開発者向けCLIツール。確認できた範囲と不確実性を開発者に示し、既存CIやレビューを補完する。

1. GitHub PR、関連Issue、差分、既存テスト、CI設定を読み取る。
2. PRの意図・受け入れ条件を抽出し、検証可能な条件に整理する。
3. 既存テストで確認できる範囲を調べ、不足する検証シナリオを提案・生成する。
4. 隔離環境でテストを実行し、実行証拠を収集する。
5. 要件・テスト・証拠を対応づけ、結果と未検証の領域をレポートする。

既存チェックの実行・集約だけにMVPを縮小しない。テスト成功は、要件全体やコード全体の絶対的な正しさの証明ではない。生成したテストや要件との対応づけも誤り得るため、実行証拠とLLMの解釈を区別し、確認範囲と不確実性を明示する。

## 初期MVPの方針

- OSS、ローカルファーストのCLIとして提供する。
- 対象言語はTypeScript / Node.js、開発プラットフォームはGitHub PRを優先する。
- LLM利用は利用者が公式の方法でログインした公式CLIへの委譲を目指す。旧BYOK接続は廃止済みであり、LLMを使わない方針へ変更するものではない。旧接続は削除済みで、対応と評価の条件は [公式CLI接続](official-cli.md) を参照する。
- まずAPI・統合テストを優先し、安全なサンドボックス／隔離環境で実行する。ローカルファーストを、対象コードをホスト上で直接実行することと同一視しない。
- ブラウザE2EテストをMVPに含める範囲は未決定。
- 出力では要件→テスト→証拠の対応を示す。テキスト/JSONレポートは実装済み。将来の出力先や拡張は未決定。

## 自前実装を最小化する原則

既存の公式ツール・標準機能を優先して、自前実装と資格情報管理を減らす。Latchは要件・テスト・証拠の対応づけに必要な処理へ集中する。

- 認証・通信・資格情報の保存と更新・非対話のモデル実行は公式ツールへ委譲する。LatchはAPIキーやログイントークンを要求・読取・保存・コピーせず、独自ログイン・更新処理を持たない方式へ移行する。
- Latchはプロジェクト境界と入力の固定、送信範囲の許可、生成結果と出典の検証、対象ワークツリーを変更しない隔離実行、要件と実行証拠のレポートを担う。公式CLIのログインを送信許可として扱わない。
- 公式機能で必要な権限制限を強制できるかを採用前に検証する。プロンプトを安全境界にせず、制約を確保できない方式は採用しない。
- 例外として自前実装する処理は、必要性と既存手段を採らない理由を設計記録に残す。現在の入力・出典・証拠の検証はLatch固有のデータ契約を守るために必要であり、モデルの構造化出力だけでは代替できない。隔離実行の現在の制約は [隔離実行](isolated-execution.md) を参照する。

旧API接続は #81で削除し、対応条件を限定してCodex CLIへ置換した。公式仕様・未改変CLIの起動確認・固定応答回帰を区別し、実アカウントでの全工程と生成品質の評価は #81の未完了範囲として残す。

## レポートで区別する状態

| 状態               | 意味                                               |
| ------------------ | -------------------------------------------------- |
| 検証成功           | 特定の要件・条件について、実行したテストが成功した |
| 検証失敗           | 実行したテストが失敗し、再現可能な情報がある       |
| 未検証             | 要件は存在するが、対応する十分な検証を行えていない |
| 要件不明確         | 要求が曖昧で、期待する結果を確定できない           |
| 実行不能・判定不能 | 環境・依存関係などにより検証できなかった           |

## 実装順の検討案

入力・要件整理 → 検証計画と不足シナリオの提案・生成 → 隔離実行・証拠収集 → 条件別レポート → 一連の実利用評価、の順に段階化する案がある。各段階単体をMVP完成とは扱わず、具体的な方式は個別のIssueで検討する。

## 未決定事項

- PR作成前のローカル差分とIssueを入力する利用仕様は [利用仕様](pre-pr-verification.md) で決定済み。入力解決・要件計画・生成テスト実行・テキスト/JSONレポートは実装済み。実API品質・悪意あるコードの封じ込めは未検証であり、既存PR取得など対象外の機能と区別する。
- PR要件抽出の精度と、人間による確認の仕組み。
- 生成テストの品質評価、既存テスト再利用の改善。
- 現行のNode.jsプロセス隔離を超える安全境界。現行方式と制約は [隔離実行](isolated-execution.md) を参照する。
- ブラウザE2EのMVPへの含有範囲。
- Markdownファイル出力、CI連携、GitHub PR投稿。テキスト/JSONレポートは実装済み。
- LLMプロバイダー、コスト制御、機密コードの扱い。
- OSSライセンス、パッケージ配布名、正式ロゴ。

追加の検討事項として、最初に対応するAPIフレームワーク・テストランナーの絞り込みや、評価用の実例・判定基準がある。これらを合意済み仕様として扱わない。
