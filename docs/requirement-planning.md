# 要件抽出と検証シナリオ計画（#24）

接続方式: #81で旧API/BYOK接続を廃止し、公式CLIへ置換しました。対応版・環境・契約上の注意・未実施の実利用評価は [公式CLI接続](official-cli.md) と [評価手順](order-api-evaluation.md) を参照してください。

この文書は、`latch plan` が入力スナップショットから要件・条件を抽出し、Vitestの既存テスト候補と不足シナリオを計画する仕様です。#24で実装した範囲は、**要件抽出と計画まで**であり、計画コマンド自体はテスト生成・対象コードや設定の実行・テスト実行・隔離実行・実行証拠の収集・PR投稿を行いません。計画に実行証拠や「検証成功」は含まれません。後続の `latch run` が [生成テストの隔離実行と証拠収集](isolated-execution.md) に従って実行証拠を収集します。

入力解決の契約は [PR作成前のローカル差分とIssueを検証する利用仕様](pre-pr-verification.md) を参照してください。

## 利用方法

```sh
latch plan \
  --base origin/main \
  --issue-file issue.md \
  --profile ~/.config/latch/llm-profile.json

latch plan --base origin/main --issue-file issue.md --profile ~/.config/latch/llm-profile.json --json
```

`latch plan` は `latch verify` と同じ `--base`・`--issue-file`・`--include-untracked` で入力スナップショットを解決し、そのスナップショットだけを後続のLLM入力に使います。`--profile` を省略した場合は環境変数 `LATCH_PROFILE` を使います。

- 終了コード0は「計画を出力できた」ことを表し、要件の達成やテスト成功を意味しません。
- 終了コード1は入力不正です。
- 終了コード2は許可不足・認証失敗・利用上限・タイムアウト・不正なLLM応答など、実行不能・判定不能です。計画を途中で標準出力へ出しません。

## 公式CLIへの委譲

Codex CLI 0.163.0の非対話実行・構造化出力を使います。認証と通信は未改変の公式CLIへ委譲し、Latchはキーやトークンを要求・解決・保存・コピーしません。Linux（WSL 2上のUbuntuを含む）上のChatGPT Plus/Proログインに対応し、WSL 1・CLI設定・管理者設定がある環境や未知の状態は推論前に拒否します。既存設定を変えない専用CODEX_HOMEでの公式ログインも利用できます。詳細と一次情報は [採用条件](official-cli.md) を参照してください。

- モデルは許可profileの `connection.model` で指定します。設定例のモデル名は、公式CLIで利用できるモデルに合わせてください。
- profileは送信許可と上限の設定です。公式CLIのログインは送信許可の代わりになりません。
- 対象コード・設定・テストを要件計画中に実行・importしません。Vitest候補はテキストとして調査します。
- 旧version 1・endpoint・apiKeyEnvは移行案内付きで拒否します。認証情報の移行・削除やAPI接続へのフォールバックは行いません。

## 許可profile

許可profileは**ワークツリー外**の利用者管理設定、または信頼したCI入力として置きます。リポジトリ内のファイルやIssue・差分・テスト本文・LLM応答を許可の根拠にしません。profileがリポジトリ内を指す場合は送信前に拒否します。

```json
{
  "version": 2,
  "id": "local-codex",
  "decision": "allowed",
  "allowed": {
    "provider": "codex-cli",
    "project": "/absolute/path/to/project",
    "dataCategories": ["issue", "diff", "tests"]
  },
  "connection": {
    "provider": "codex-cli",
    "model": "gpt-5.4"
  },
  "limits": {
    "maxRequests": 2,
    "timeoutMs": 30000,
    "maxOutputBytes": 200000,
    "maxInputCharacters": 60000
  }
}
```

`decision` は次のとおりです。

| 値        | 挙動                                                                      |
| --------- | ------------------------------------------------------------------------- |
| `allowed` | `allowed`の範囲に一致する送信を、同一範囲では追加確認なしに継続する       |
| `denied`  | 保存済みの許可より拒否を優先し、送信せず終了コード2                       |
| `revoked` | 取り消しを優先し、送信せず終了コード2。以前のレポートの許可記述も使わない |

- `allowed.provider`・`allowed.project`・`allowed.dataCategories` が送信範囲です。`connection`のproviderが許可範囲と一致しない場合や、現在のリポジトリ・Issue有無から増えたデータ区分は「範囲拡大」として送信しません。
- 差分の更新だけでは許可を失効させません。同じ範囲の再実行はprofileを再利用します。
- 非対話実行（CIなど）でも確認待ちにしません。許可profileがない・拒否・取り消し・範囲拡大・未ログインの場合は、必要な設定を標準エラーへ案内して終了コード2を返します。
- `project`はリポジトリルートの絶対パスです。移動・別プロジェクトは新しい許可として扱います。
- 認証情報らしきキー（`apiKey`・`token`・`authorization`・`headers`など）を含むprofileは拒否します。

## データ区分と送信内容

| 区分    | 内容                                                     |
| ------- | -------------------------------------------------------- |
| `issue` | 解決済みスナップショットのIssue本文・状態・出典          |
| `diff`  | コミット済み・未コミット差分、明示指定した未追跡ファイル |
| `tests` | 探索したVitestテスト候補のパス・テスト名・抜粋           |

- Issue・差分・テスト本文は信頼できないデータとして区切り、システムプロンプトで命令として扱わないよう指示します。本文中の「許可する」「全ファイルを送る」などの記述は、実行権限・送信許可・設定変更として扱いません。
- 既知の認証パス（`.claude/`・`.codex/`・`.env*`等）は入力・探索・隔離コピーから除外し、Issueにも指定できません。任意のソース中の秘密を検知するものではないため、入力に秘密を含めないでください。
- #22の評価専用テスト・正解データ（`evaluation/`、`cases.json`、`expected.json`、`changes/*.patch`など）は、差分・テスト候補のどちらからもLLM入力へ混入させません。除外した場合は計画の警告に残します。
- 入力が大きい場合は上限まで切り詰め、切り詰めたことを未検証事項として表示します。

## データ契約

計画は `phase: "requirement-planning"`、`verification: "not-run"` を持ちます。主な要素は次のとおりです。

| 要素               | 内容                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------- |
| `requirements`     | 要件。`id`・本文・出典・由来・状態・条件を持つ                                           |
| `conditions`       | 要件を検証可能な条件へ分けたもの。`id`・出典・状態・既存テスト候補ID・不足シナリオを持つ |
| `source`           | `issue:<path>#L<行>` または `diff:<path>`。入力に存在する箇所だけを受け付ける            |
| `origin`           | `issue-explicit`（Issue明示）または `diff-inferred`（差分からの推定）                    |
| `testCandidates`   | Vitestの既存テスト候補。実行結果ではなく、対応する条件IDだけを持つ                       |
| `missingScenarios` | 後で検証する不足シナリオ。説明・理由・状態を持ち、`evidence` は常に `none`               |
| `unverified`       | 未検証事項・LLM応答の品質評価の未実施など                                                |
| `warnings`         | Issueなし・closed Issue・評価データ除外・入力切り詰めなど                                |

IDは出典・由来・本文から決定的に作り、同じ入力と同じ抽出内容では再実行しても同じIDになります。IDはLLMに作らせず、入力に存在する出典とテスト候補IDを検証してから付与します。存在しない差分パス・Issue行・テスト候補IDを返した応答は不正なLLM応答として拒否します。

### 状態

計画段階では、条件は次のいずれかです。

| 状態       | 意味                                                  |
| ---------- | ----------------------------------------------------- |
| 未検証     | 要件・条件は存在するが、実行した検証・証拠がない      |
| 要件不明確 | 要求が曖昧、またはIssue省略などで期待値を確定できない |

「検証成功」「検証失敗」は計画には現れません。既存テスト候補は「未実行」、不足シナリオは「計画のみ」と表示します。Issueがclosedの場合は状態・出典を保持し、過去要件を現在の達成として扱わない旨を警告・未検証事項へ残します。

## 呼び出し量・時間・再試行の上限

- `maxRequests`は1〜3。plan/runごとのCLI推論起動の上限です。planは1回、runは生成と修復の合計で上限を守ります。自動再試行はしません。CLI内部のHTTP要求数・token数・費用の上限と同義ではありません。
- `timeoutMs`は1,000〜120,000ms。版・認証確認を含む起動単位の期限です。タイムアウトやSIGINT/SIGTERMでプロセスグループを終了します。
- `maxOutputBytes`は1,000〜1,000,000 bytes（既定200,000）。stdout/stderrの合計を制限し、生のエラーは出力しません。旧 `maxOutputTokens` は廃止しました。
- `maxInputCharacters`は1,000〜200,000文字（既定60,000）。要件計画ではsystemとuserの合計で制限し、切り詰めを未検証事項へ残します。生成・修復で超過した場合は送信しません。
- 構造化出力を受け取った後も、Latchのデータ契約と出典を検証します。不正な応答を部分的に成功として採用しません。

## 人の確認・修正・再計画

1. テキスト出力または`--json`で、各要件・条件の`source`がIssueの該当行または差分パスを指しているか確認します。
2. `origin`が「Issue明示」と「差分推定」で正しく分かれているか確認します。
3. `要件不明確`の条件は、期待値を推測で埋めず、Issueの受け入れ条件や用語を具体化します。
4. 既存テスト候補は未実行です。候補が条件を実際に確認できるかは、後続のテスト実行・証拠収集で確認します。計画だけで検証済みとしません。
5. 修正後、同じ`--base`・`--issue-file`・`--profile`で`latch plan`を再実行します。同じ出典・本文のIDは維持され、入力や抽出内容を変えた場合は新しいIDになります。
6. 許可範囲を広げる場合は、送信先・プロジェクト・データ区分を利用者が許可profileへ明示してから再実行します。差分の更新だけでは許可は失効しません。
7. 取り消す場合はprofileの`decision`を`revoked`にします。拒否は`denied`です。どちらも保存済みの許可より優先します。

`--json`の出力は、後続の `latch run` によるテスト生成・隔離実行・証拠収集が参照するデータ契約です。人が修正する場合は、Issueや許可profileなど入力側を直して再計画する方法を基本とし、計画JSONの状態を実行証拠として書き換えません。

## 検証の限界

- 自動テストは固定したLLM応答を使い、抽出・出典検証・許可判定・失敗時の停止を確認します。公式CLIの実利用品質評価は別です。
- このリポジトリの自動テストでは実際の有料モデルを呼びません。実ログインでの抽出精度・幻覚・コスト・レイテンシは未検証です。
- 要件の網羅性、LLMの解釈の正しさ、既存テスト候補が条件を十分に確認できることは保証しません。テスト生成・実行・証拠収集は #25 の `latch run` の範囲で、計画の成功を実行証拠として扱いません。
