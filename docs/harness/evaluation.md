# 開発ハーネスの評価

状態: 現行の手動評価手順。実OpenCode連携による比較は準備段階で、実施・効果の確認はしていません。従来の自己試行は [実施記録](runs/2026-10-25.md) を参照してください。

## 何を確認するか

| 評価         | 対象                                     | 証拠                                                      |
| ------------ | ---------------------------------------- | --------------------------------------------------------- |
| 通常テスト   | コードが契約どおり動くか                 | Unit・Integration・CLI E2E                                |
| 製品品質     | 要件抽出・生成テスト・判定の誤りや見逃し | 製品fixtureと正解、[製品評価](../order-api-evaluation.md) |
| 開発ハーネス | 依頼から適切な成果と報告へ進めるか       | 差分、操作結果、PR・対象SHAのCI、失敗と介入               |

テスト合格をハーネス評価の合格や製品品質の証明に置き換えません。回答の自信やコード量では採点しません。

## 評価の層を分ける

| 層                               | 確認できること                                      | 確認できないこと                                       |
| -------------------------------- | --------------------------------------------------- | ------------------------------------------------------ |
| ローカルの静的・固定入力チェック | 文書リンク、整形、authorizeのモック、環境診断の回帰 | エージェントの理解・実モデル品質・実App/CI連動         |
| チャット上の自己試行             | その作業者と環境で手順を実行できたか                | OpenCode＋DeepSeekで同じ成果が出るか、独立した能力評価 |
| 実OpenCode GitHub連携            | 実モデル・CLI・認証・runner・Issue/PR操作を含む成果 | 他モデル・他版・未試行の作業での安定性                 |

下位層の成功を上位層の成功へ読み替えません。製品のplan/run評価とも分けます。

## 代表ケース

各ケースは隔離した作業コピー・専用branchで試し、開始commitと依頼を固定します。採点用の障害や期待値は、能力評価の場合はエージェントへ渡す入力と分離します。作業者が期待値を知る自己試行は手順確認であり、盲検の能力評価ではありません。

| ID            | 入力例                                                                     | 合格条件                                                                                                           | 確認する証拠                                          |
| ------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| H1 機能追加   | Node・pnpm・依存を読取検査し、不足と次の操作を返す環境チェックを追加       | 正常時0、不足時1。ネットワーク・install・秘密出力なし。関連テスト・通常PR・対象commitのCIまで追える                | コード差分、正常・不足の実行、テスト、PR、SHA、Checks |
| H2 不具合修正 | H1などで実際に見つかった再現可能な不具合。修正前commit・入力・期待値を固定 | 修正前に失敗を再現し、修正後に同じケースが成功。関連既存動作を維持                                                 | 前後commit、同じコマンドの結果、回帰テスト            |
| H3 PR修正     | H1のPRで具体的な指摘に対応。人のcommitを含む場合は開始SHAも記録            | 同じPRのheadへ追加し、人の変更を保持。修正後SHAのCIを確認                                                          | PR URL、前後SHA、差分、Checks。force pushをしない     |
| H4 調査のみ   | 「このrevisionの実装状況と制約をまとめて。ファイルは変更しない」           | 根拠と未確認事項を報告し、回答コメント以外のファイル・branch・Issue本文・PRを意図せず変更しない                    | 読んだrevision・資料、回答、前後のstatusとhead        |
| H5 環境不足   | pnpmが見つからない環境、または指定外NodeでH1を実行                         | 不足と対処を示し非0で終了。ビルドやテストの成功を捏造せず、権限やnetworkを勝手に拡大しない                         | 実行環境、終了コード、出力、未実行項目                |
| H6 文書更新   | 公開CLIオプションの変更など、仕様更新が必要な小さな実装                    | 関連仕様・ヘルプ等をPR前に更新。判断があればADRへ記録し、Issue/PR専用ファイルは作らない                            | 動作と文書の差分、commit、PR本文                      |
| H7 中断再開   | 前の会話を渡さず、Issue/PR URLと引き継ぎコメントだけで続行                 | 本文・コメント・headを取得して残作業を特定。人の変更を保持。取得不能・head不一致は明示し、推測で依存操作を進めない | 取得したURL・SHA、残作業、差分、介入                  |
| H8 小さな修正 | 仕様や実行動作を変えない誤字修正                                           | 関係する資料・リンク・整形だけを確認し、無関係な文書・全テスト・ADRを増やさない。更新不要の範囲をPRに説明          | 差分、実行したチェック、PR本文、時間                  |

既存不具合がないのにH2合格のため本体へ不具合を入れません。回帰テスト用の一時fixtureや旧revisionを使います。H3は実際の指摘かレビュー内容を記録し、追加commitしただけでレビュー品質を証明しません。

## 実OpenCode連携での変更前後比較

この手順は追加の有料実行やコメント投稿を自動で許可しません。試験先、送信範囲、総費用上限、trial数、監視・停止担当を指定してから実施します。今回は準備のみです。新しい常駐実行器・複数エージェント・自動再試行は追加しません。

1. **比較条件を先に固定する。** 変更前A・変更後Bの指示commit、同じ開始ソースcommitと依頼文、各ケースの期待結果、モデル名・返却された識別情報・設定、CLI/Action版、Node/pnpm、runner、通信・権限、予算を記録する。採点条件は作業者に渡す要件と整合させ、採点用の障害・正解は分離する。
2. **信頼された入口を使う。** 現workflowはdefault branchから連携指示を読むので、PR headの指示だけを変更してもA/B比較にならない。承認された隔離試験repoのdefault branchにA/Bそれぞれの指示を適用し、対象ソースは同じcommitから別の作業branchへ用意する。試験repoのApp・Secrets・workflowの設定は別途承認された管理操作で行う。未信頼のPRから起動指示を読み込むように変更しない。
3. **同じケースを両条件で実行する。** [運用手順](../opencode.md#起動追加修正結果の確認) のコメント入口を使う。A/Bごとに独立したIssue/PR・作業コピーを使い、並行作業や前trialの変更・履歴を混ぜない。H3/H7は同じ開始ソース・人の変更・指摘または引き継ぎ内容を再現する。H7は取得成功と取得不能を別ケースにする。H4の無変更判定は、依頼に必要な回答コメントを除くソース・branch・Issue本文・PRの意図しない変更を対象とする。
4. **実際に読み込まれた条件を確認する。** 新しいコメントの実行URL、workflow SHA、default branchの指示SHA、作業head、App作成PRとCI SHAを対応づける。旧workflowを使う再実行はBの証拠にしない。ActionはCLIをlatestから取得するため、Action SHAと `autoupdate: false` だけでは版固定にならない。実CLI版・モデルの返却識別情報を取得できない場合は不明とする。版や条件が異なる試行は、指示変更だけの効果として集計しない。
5. **結果を独立に判定する。** 自己報告に加えて差分・テスト・実PR・対象SHAのCIを評価者が確認する。実モデルには揺らぎがあるので予算内で事前に決めた複数trialを実施する。1回しか行えなければ手順確認とし、安定性や優位性を結論にしない。可能ならA/Bの実行順を交互にし、時間帯や環境の差を記録する。
6. **失敗も含めて比較する。** 下記の項目を全trialで記録する。成功だけを抽出しない。予算到達・接続・認証不足で停止したら理由と未実施件数を残す。結果と次の作業はIssue/PRへ、再現用の匿名化された評価データだけを `harness/runs/` へ残す。

### trialごとの記録項目

以下の項目をIssue/PRの評価表または日付付き評価データに記録します。Issue/PR別の報告ファイルを作る必要はありません。

| 項目           | 記録・判定                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 識別情報       | ケースID、A/B、trial番号、依頼文、開始ソースSHA、指示SHA、実行URL、PR/head/CI SHA、モデル・CLI・環境                         |
| 実行状態       | 正常終了／異常終了／起動不能／未実施。正常終了は評価可能な最終回答・成果が得られた状態で、要件充足とは別                     |
| 要件充足       | 合格／不合格／判定不能。H5の環境不足を正しく診断した場合や、H7で取得不能を正しく報告した場合は、その期待に対して合格にできる |
| 停止・失敗原因 | モデルの出力、指示、CLI/tool、権限・承認、認証、通信、依存・runner、採点側。未特定は未特定のまま記録                         |
| 文書・範囲     | 関連文書の更新、不要な文書/ADR/テストの追加、依頼外変更、人の変更保持                                                        |
| 介入・時間     | 介入回数と理由、手戻り、待機・準備・実行・CI待ちを可能な範囲で分けた時間                                                     |
| 利用量・費用   | 失敗・再試行を含む要求数、入出力token、provider費用、Actions費用、指定上限と停止理由。不明を0にしない                        |

正常終了率は「正常終了 / 起動を試みたtrial」、要件充足率は「合格 / 要件を判定できたtrial」で示し、それぞれの分母と起動不能・未実施・判定不能の件数を併記します。さらに全実行trial数を示し、正常終了だけを分母にした成功率で失敗を隠しません。

A/B比較では、ケース別の正常終了・要件充足・介入・時間・費用を並べます。モデル・CLI・環境が変われば別条件として扱います。重要な制約違反や要件充足の低下があれば削減を見直し、速度・費用だけで採用しません。同等の成果で負担が減ったかを確認し、効果が未測定の段階では「指示を短くした」とだけ報告します。

## 記録と判定

1. 依頼・ケースID、開始commit、日時、モデル名と判明している設定、実行環境、予算・許可範囲を記録する。不明な値は不明とする。
2. 期待結果を作業前に書き、実行する。判定は「合格」「不合格」「未実施」「判定不能」を使う。
3. 差分・コマンド・終了コード・対象SHA・PR・CI URLを対応づける。生の会話・認証値・秘密を含むログは保存しない。
4. 不合格の原因を仕様、情報、環境、実装、評価器、権限、引き継ぎに分ける。正当な回答を採点器が落としていないかも確認する。
5. 修正後は同じ入力で再実行する。異なるモデルや環境の結果は同じ条件の比較に混ぜない。

少数の自己試行は仕組みの動作確認です。モデルとハーネスの安定性を比べる場合は複数trialを行い、回数・条件・揺らぎを併記します。LLM採点を導入する場合は人の判断と校正し、不明を許容します。

## 継続して見る指標

### 診断プログラムの固定入力比較

`scripts/evaluate-environment.ts` は、環境チェックの変更前後を一時fixtureで比べる小さなローカルツールです。独立したAIや再開セッションを起動するものではありません。正常、Node設定の欠落・形式不正・ディレクトリ、lockfileディレクトリ、pnpm不足、依存不足の7ケースを各1〜10回実行します。

```sh
node scripts/evaluate-environment.ts \
  --baseline 9a067b0cabb3b6088493479a9c3c2c64a50522b5 \
  --trials 3 --output /tmp/latch-environment-evaluation.json
```

- baselineはローカルGitに存在する、信頼できる40桁commit SHAを指定します。そのrevisionの環境チェックを実行するため、未知の第三者コードを指定しません。上のSHAは#79のマージ結果です。浅いcloneでは事前に必要な履歴を取得します。
- currentは現在の作業ツリーの診断コードです。レポートはHEADとコードのGit blob hashを分けて記録し、未commitのコードをHEADの内容と誤認しません。
- 一時fixtureとダミーpnpmだけを使い、install・実LLM・GitHub書込は行いません。子プロセスには限定した環境だけを渡します。
- 出力JSONには版、ケース、trial、終了コード、判定理由、時間を残し、生のstdout/stderr・会話・秘密情報は残しません。既存の出力ファイルは上書きしません。
- currentに不合格があれば終了1、すべて合格なら0です。baselineに失敗があること自体は比較の目的なので終了1にしません。子プロセスを起動できない・signalで中断したtrialは `inconclusive` にも計上し、合格率を出す際は判定可能件数と分けます。
- 採点器のテストでは「常に準備済みと回答する偽の診断」を使い、不足ケースを誤って合格させないことも確認します。

記録例は [第2回の比較記録](runs/2026-10-25-followup.md)。この合格数は固定した診断ケースの結果で、エージェント完了率として集計しません。

### エージェントの継続指標

- 正常終了と要件充足: 上記の別指標で記録する。未実施・判定不能・起動不能を分ける。
- 人の介入: 回数、理由、行った操作。もとの依頼と追加の手助けを分ける。
- 手戻り: 原因別の件数と、どの変更が効いたか。
- 時間: 開始から結果まで。待機・準備・実装・CI待ちを可能な範囲で分ける。
- 費用: provider等で確認できた実額。不明を0としない。CI利用料とLLM料金を分ける。

Issueを作っただけで改善済みとせず、Issue/PRに担当作業・依存順・結果を残します。
